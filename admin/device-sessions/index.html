    Device sessions (mobile unlock)

    Device sessions let the patient mobile app stay signed in on a phone and reopen with the device's biometrics or screen lock, instead of sending an email code on every visit.

    Menu: Configuration > Authentication

    What actually protects the session

    The credential is an EC P-256 key pair generated inside the phone's secure hardware — the Android Keystore or the iOS Secure Enclave. The private half cannot be exported, and the platform is instructed to refuse every use of it until the user has authenticated:

    • setUserAuthenticationRequired(true), with per-operation authentication
    • setInvalidatedByBiometricEnrollment(true) — enrolling a new fingerprint destroys the key
    • setUnlockedDeviceRequired(true) where the platform supports it
    • StrongBox (a dedicated security chip) when the device has one

    This is stronger than the usual "ask for a fingerprint, then read a stored secret" pattern, which a rooted device or a compromised WebView can bypass. Here the secure element itself refuses the operation, so there is nothing to intercept.

    The server stores only the public key. A leak of the HCW@Home database therefore cannot be replayed to impersonate a device.

    Signing in is a challenge-response: the server issues a random nonce, the phone signs it behind an authentication prompt, and the signature is exchanged for a normal short-lived session. Nonces are single-use.

    Settings

    Setting Default Effect
    enable_device_sessions On Master switch. When off, the app never offers device unlock and the endpoints refuse every request.
    device_session_lifetime_days 180 Days of inactivity before a device session expires. The window slides forward on every use, so an active user is never signed out. 0 disables expiry.
    device_session_max_per_user 10 Enrolling beyond this revokes the least recently used device. 0 removes the limit.
    device_session_min_security_level Hardware-backed Minimum key storage accepted at enrolment: software, hardware-backed (TEE) or StrongBox.
    device_session_require_attestation Off Refuse enrolment unless the device's certificate chain validates to a Google root. See below before enabling.

    Leaving device_session_min_security_level at hardware-backed is the recommended setting. Lowering it to software would accept devices where the key is not protected by a secure element, which removes the guarantee described above. A device that cannot meet the configured level is simply not offered the feature and keeps using the normal login.

    Devices that are not eligible

    • Web browsers. There is no hardware-backed, authentication-gated key store in a browser; the credential would sit in ordinary storage while looking like a security feature. The feature is native-only by design.
    • Phones with no biometrics and no screen lock. Nothing would protect the credential, so the app does not offer it.
    • Temporary accounts. Accounts created for a single appointment are deleted automatically, so their device credential would outlive the user it belongs to.

    Revoking a device

    Users revoke their own devices from Profile > My devices. Administrators can revoke any device from Users & Authentication > Device sessions, individually or in bulk.

    Revocation takes effect immediately, including for sessions already open: the access token carries the device identifier and is checked against a revocation list on every request. Revoked devices are kept in the list, marked as signed out, rather than deleted — a user needs to be able to confirm that a lost phone really was cut off.

    When a phone's security changes (a new fingerprint enrolled, the screen lock removed) the platform destroys the key. The app detects this, clears its local state and asks for a normal sign-in. There is no fallback to a weaker storage mechanism in that situation, by design. The stale server-side row expires on its own and stays revocable from another device.

    Attestation

    At enrolment the device sends the attestation certificate chain produced by its secure element. HCW@Home:

    1. reads the reported security level, the verified boot state and the challenge out of the leaf certificate;
    2. validates the chain — signatures, validity dates, and an anchor that is or is signed by one of the Google roots pinned in the repository (backend/users/data/google_attestation_roots.pem, never fetched at verification time);
    3. checks each certificate against Google's revocation list, cached for six hours.

    The outcome is stored as Attestation verified on the device session and shown in the admin list.

    Attestation is used rather than Play Integrity because it works on devices without Google Play Services and on installations distributed outside the Play Store, which is the common case for field deployments.

    Before enabling device_session_require_attestation

    The check is off by default on purpose. Look at the Device sessions admin list first and see what your fleet actually reports. Devices that will be turned away include:

    • manufacturers that ship no key attestation at all;
    • devices running a custom image, whose chain does not lead to a Google root;
    • devices whose attestation batch key Google has revoked.

    If the revocation list cannot be fetched, its result is treated as unknown rather than revoked: a network outage at Google should not stop every enrolment on the instance. The miss is logged.

    Data protection (GDPR)

    A device session record contains:

    Data Purpose Retention
    Device public key Verifying the signed challenge Life of the session
    Device identifier Naming and revoking the device Life of the session
    Device label, platform, app version Letting the user recognise their device Life of the session
    IP address and user agent of last use Letting the user spot a session they do not recognise Life of the session
    Attestation chain, security level, verified boot state Confirming the credential is hardware-protected Life of the session

    Legal basis: performance of the service (keeping the user signed in on a device they chose to trust).

    Retention: device_session_lifetime_days (180 days of inactivity by default). Revoked sessions are retained so the user can see the revocation, and are removed with the user account.

    No private key material, and no health data, is ever stored on the server or transmitted by this mechanism. The cryptographic material never leaves the device.

    Right of revocation: users can revoke any of their devices at any time from Profile > My devices, without contacting an administrator.

    Rooted or tampered devices: the verified boot state is read from the attestation chain, recorded, and visible in the admin. An instance that needs to exclude such devices should enable device_session_require_attestation — after checking the admin list, as described above — and may additionally raise device_session_min_security_level to StrongBox.
